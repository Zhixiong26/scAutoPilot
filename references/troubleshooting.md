# Troubleshooting and recovery

- Input signature changed: create a new run ID; do not reuse checkpoints. Reuse the same run ID only to resume its unchanged signed plan.
- Missing full-validation evidence: run `validate_project.py --mode full`; production submit also creates and caches matching evidence when absent.
- A full validation reads no ALLC files: check `counts.allc_cells` in `.workflow/validations/<signature>.full.json` — 0 means the selected routes included no methylation route, so nothing was checked, not that everything passed. `allc_cells` counts the ALLC files the selected routes included and `allc_validation` the ones actually read; `inspect_run.py` prints both in `run_summary.json` next to the verdict. The route scope is deliberate: `input_signature` contains the routes, so enabling a methylation route changes the signature and forces the full validation to be repeated rather than reusing a record that never covered it.
- A full validation takes hours: it is reading every ALLC file end to end, and that is the work, not overhead. Estimate from what it actually sustains — about **3 MB/s per process**, so the default 32 processes read a 132 GB sample in **23 minutes** and a 1 TB project in **about 3 hours**. It is already distributed across `validation_parallel` chunk jobs of `validation_processes_per_task` processes each; raise both together, a step at a time, if the shared filesystem tolerates it. The per-process rate at 32-way concurrency was within 10% of a single process reading alone, so the default is not yet filesystem-bound. Do not replace the processes with threads: the same check through threads measured 2.3× *slower* than reading the files one at a time, because the per-line loop holds the GIL. The chunk jobs are in `.workflow/validations/allc-fanout/`, with `chunk_NNN.manifest.json`, `chunk_NNN.out.json`, and `logs/`.
- An ALLC validation chunk failed or timed out: the validation is invalid and the error names the chunk. Fix the cause (a node that could not read the mount, a `time` limit shorter than the chunk needs), then re-run the same `validate_project.py --mode full`. Chunks whose manifest still matches are reused, so only the failed chunk is resubmitted — deleting its `chunk_NNN.out.json` is never necessary for that.
- Validation refused because a chunk accounted for the wrong number of files, or was built from a different manifest: that is the merge failing closed, not a bug. It means a chunk result cannot be attributed to the file list it was supposed to cover, and reporting a smaller validated set as valid is the failure this check exists to prevent. Re-run the validation; if it repeats, the chunk results on disk are stale and can be removed as a set.
- A submission reports `full_validation_skipped: true`: `--skip-full-validation` was used and no matching evidence was on disk, so the run was submitted without a full read of its inputs. There is no evidence file to inspect, by design — a record saying the inputs were read would outlive the run that did not read them. Read the field on `plan.json` or on any task record in `submissions.json`, or in `inspect_run.py`'s output. Submit again without the flag to produce the evidence; a run that later reused evidence on disk says `full_validation_skipped: false` and is fully validated.
- Missing task artifact with a stale marker: resubmit the same run ID; the task is treated as incomplete and rerun.
- A fix to this skill has no effect on a project: the ten files in `RUNTIME_TOOLS` (`_common.py`, `validate_project.py`, `submit_workflow.py`, …) are **copied into `<project>/tools/` when the project is generated**, not imported from the skill, so a project generated before the change keeps running the old code and the repaired failure repeats identically. Copy the changed files from the skill's `scripts/` into the project's `tools/`, or generate a fresh project. Either way the code signature changes, so the project's recorded validations are invalidated and have to be re-run — expected, not a new fault.
- Resource floor cannot fit: wait or choose an allowed larger partition; do not undersize.
- Refused: "this host is a Slurm submit host (login node)". A planned task may not execute there. Submit through the DAG with `scheduler.backend: slurm`, or run the orchestrator inside an allocation (`salloc`, or `srun --pty bash`) — inside one the role is `compute` and local execution is legitimate. Do not reach for `--allow-login-execution` to get past it: that flag names one run, is recorded in `submissions.json` and in every covered task's `task_status.json` as `login_execution: true`, and bypasses the DAG's dependency ordering and `max_parallel` throttling. Nothing was executed when the refusal appeared, and the refusal wrote no task evidence, so there is nothing to clean up.
- The refusal appeared for a `Methylvi/*/run.sh` call that used to work: it needs an allocation as well as `SCMO_STANDALONE_ACK=1`. The packaged `.sbatch` wrappers set that acknowledgement and run inside a job, so submit those instead.
- A run executed on the login node: read `.workflow/runs/<id>/submissions.json` for `job_id` values starting `local_`, or `login_execution: true`, or `backend_declared` differing from `backend_effective`. `tools/inspect_run.py` flags such tasks in `run_summary.json` under `login_execution_tasks` and warns on stderr. Each task row separates the two roles that a run involves: `submitted_from_host_role` is the host that called the scheduler, and `executed_on_host_role` is the host the task itself ran on, read from its `task_status.json`. They differ on a healthy run — `submit` and `compute` — so neither one alone answers "where did this run". Records written before the host role was recorded at all have no `host_role` field; the synthesized `local_` job id is the only marker they carry. Re-running the work through a Slurm backend is the fix — the outputs are not wrong, but nothing scheduled them, so a login-node failure would have lost them silently. A `local_` id on a host whose submission record says `host_role: standalone` is not flagged: on a machine with no controller there is no compute node to submit to.
- `scheduler.partitions` was filled in without being declared: a project generated on a host whose `sinfo` answered has its allow-list inferred from the partitions that host reported, so check it against what your site permits. The Report says which partitions were observed and that they were inferred. Changing it changes the input signature, so a recorded full validation has to be repeated.
- A `local` project on a host that has a Slurm controller: submission promotes it to Slurm rather than running it in place, and `submissions.json` records `backend_declared: local` beside `backend_effective: slurm`. If the promotion then refuses for an empty partition allow-list, declare `scheduler.partitions` — the error names the partitions `sinfo` reports.
- `Data/<name>` does not resolve, or a stage fails on an input that is present elsewhere: the declared source is not reachable from where the work runs. `python tools/link_data.py --project PROJECT` prints each entry's state and origin without changing anything; a state of `dangling` means a correctly placed link whose target this host cannot see, which is a mount question, not a link question. Re-run with `--execute` after fixing it. Never repair it by editing a stage script to read the original path.
- A `url` source was never fetched: generation declares downloads but does not perform them. `python tools/link_data.py --project PROJECT --execute` fetches it to a dot-prefixed sibling, verifies the declared sha256, and moves it into place only then; a mismatch removes the incomplete file and leaves `Data/` untouched.
- `Data/<name>` already exists and is not what `data.sources` declares: `link_data.py` refuses rather than overwrite. Decide which copy is the real input, move the other aside, and re-run. Reach for the tool rather than `ln -s` by hand, so `config/project.yaml` keeps matching what is on disk.
- Reference defaults look wrong for this genome: the bundled hg38 files are applied only to a human project with a methylation route and an hg38 `genome_id`. A project that declares another organism or genome gets no defaults and a warning naming the key to declare; set `references.chrom_sizes` and `references.blacklist` in the intake, or in `config/project.yaml` — the latter changes the input signature, so a recorded full validation must be repeated. An intake that declares no genome at all gets the hg38 defaults and `references.genome_id: GRCh38` written for it; the Report records that inference, and a project whose data is not hg38 must override both the key and the files before any run.
- Failure after training: recover only missing plots/summary when signatures match.
- Annotation guard failed: review current markers and clusters; do not reuse old numeric mappings.
- Recording a reviewed annotation: with a candidate run finished, `tools/record_annotation_review.py --project . --run-id ID --worksheet review.tsv` writes one row per cluster seeded with the run's own majority label, and the same command with `--mapping review.tsv` records it. The tool refuses a placeholder label, a worksheet that does not cover the run's clusters exactly, and an existing worksheet it would overwrite, because each of those would replace a review with something else. It binds the run's `analysis_signature` and cluster set into the profile, so editing `leiden.resolution` or re-running with different data makes the old profile unusable by design — review again rather than transplanting the mapping. It writes `config/annotation.yaml` unless `annotation.profile` names another path; a profile nothing points at is still unreviewed, so set `annotation.profile`, then `annotation.review_status: approved`.
- DMR route disabled: set `annotation.review_status: approved` only after reviewing labels and remove placeholder cell types.
- Fractional counts, `mc > cov`, duplicates, or manifest mismatch are hard failures.
- Submitted Slurm jobs are snapshots; later script edits do not alter them.
- Missing environment stage: run `tools/bootstrap_environments.py --project PROJECT` to inspect the plan, then add `--execute`. Do not repair it by upgrading a shared environment.
- Override command exited zero but task failed: inspect `process_return_code`, `failure_stage`, and `error` in `task_status.json`; create `<task_dir>/task_outputs.json` as a JSON object — `{"artifacts": ["/abs/path", ...]}` — whose list is non-empty and whose paths are absolute and already exist. A bare JSON list is rejected with "not a valid JSON object", and a relative path is rejected separately.
- Failed Conda creation: inspect `.workflow/environment-bootstrap/` and the incomplete isolated prefix. The bootstrapper intentionally does not delete it; choose a new empty prefix after correcting channel, network, or storage problems.
- Standalone wrapper needed: `Scripts/Common/scheduler_flags.sh PROFILE` prints the `sbatch` resource flags for one profile, so a wrapper can be checked against the DAG's allocation without submitting. A wrapper that carries its own `#SBATCH` resource directive is a defect — resources come from the profile.
- Route config reports an unset variable: route configs require only what the route cannot run without. Check `00_experiment_config.sh` for the shared experiment values and the route's own `00_*_config.sh` for its layout; a summary stage does not need the DMR source paths a prepare stage does.
- Two routes disagree about a root: `SCMO_MVI_EXPERIMENT_ROOT` is the parent of every route, while `SCMO_MVI_ROOT` is the `allcools/` route root alone. Confirm which one a script means before overriding either.
- Run record missing, stale, or absent for one run: run `tools/update_report.py --project PROJECT` to rebuild the whole run log from `.workflow/runs/*/run_summary.json`, or add `--run-id ID` to require that one run to exist. Never edit inside the `SCMO-RUNLOG` region by hand — a human note belongs above it, where the tools never write. Re-inspecting a run updates its record in place and moves it to the end of the log, which is expected and not a duplicate.
- Root README looks out of date: that is intended. It is written once at generation and frozen, so it never reports progress or results. Read `Report.md` for the run history, and regenerate the project if the configuration itself changed.
- Documentation write failed during inspection: the run's verdict is unaffected. Find the recovery command in the stderr warning; a full disk or a read-only checkout is the usual cause.
